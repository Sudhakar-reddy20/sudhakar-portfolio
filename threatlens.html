01 / PROBLEM

Why I built it

SSH authentication logs contain useful incident clues, but an analyst still needs to identify patterns across timestamps, source addresses, accounts, and outcomes. ThreatLens turns a local log file into normalized events and highlights two patterns that deserve triage.

Repeated authentication failures

Several failed attempts from one source within a defined time window may indicate password guessing or a misconfigured client. Context is required before classifying it as malicious.

Success after failures

A successful login after repeated failures from the same source raises the priority of the investigation. It does not, by itself, confirm that an account was compromised.

  1. Read: load a local authentication log file and skip blank lines.
  2. Parse: extract supported SSH records into structured events, validating timestamps, IP addresses, and source ports.
  3. Detect: group events by source IP and apply configurable time-window rules.
  4. Preserve: attach the original matching log lines and usernames to each alert.
  5. Report: export structured JSON and CSV output for review.

03 / DETECTION LOGIC

Two rules, explicit evidence

TL-SSH-001HIGH · PROJECT LABEL

Repeated SSH authentication failures

Default threshold5 failures
Time window10 minutes
GroupingSource IP

The detector sorts events by timestamp, then finds the first rolling window that reaches the failure threshold. It emits one alert for each qualifying contiguous failure burst, rather than generating overlapping duplicate alerts for every subsequent window. A quiet gap longer than the configured window starts a new burst.

Alert evidence includes the original lines in the first qualifying window and all usernames targeted in that window.

TL-SSH-002CRITICAL · PROJECT LABEL

Successful login following repeated failures

Default threshold3 prior failures
Time window10 minutes
GroupingSource IP

For each successful login, the detector checks for the configured number of failures from the same source IP during the preceding time window. The evidence includes the preceding failures and the successful event, including usernames involved.

Severity labels are project-defined triage priorities, not a universal incident classification standard.

04 / SAMPLE INVESTIGATION

What the included dataset shows

The repository includes a synthetic 11-line SSH log sample. Ten records are supported authentication events (eight failures and two successes); one connection-close record is unsupported by the current parser and is counted rather than silently treated as an authentication event.

All sample IP addresses are from documentation-only ranges. They represent synthetic lab data, not real attackers or production hosts.

05 / REPRODUCE

Run it locally

ThreatLens is a local CLI. Clone the repository, create a virtual environment, install the project, and analyze the included synthetic log.

git clone https://github.com/Sudhakar-reddy20/threatlens.git
cd threatlens
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e ".[dev]"
threatlens analyze sample_logs/auth.log --year 2026

By default, reports are written to reports/threatlens_report.json and reports/threatlens_report.csv. Thresholds and the output directory can be configured through CLI options.

06 / ENGINEERING

Implementation and quality checks

Core modules

  • parser.py — SSH event parsing and validation
  • detector.py — time-window detection and correlation
  • reporter.py — JSON and CSV serialization
  • cli.py — command-line arguments and orchestration

Testing and safety

  • pytest tests cover parsing, thresholds, time boundaries, deduplication, evidence, and CLI behavior.
  • GitHub Actions runs the project test workflow across supported Python versions.
  • CSV output includes basic formula-injection mitigation.
  • Malformed or unsupported records are skipped and counted.

Python 3.10+ · Standard library · pytest · GitHub Actions · MIT License

07 / LIMITATIONS

What this project does not claim

  • It analyzes local files; it does not ingest live logs or monitor endpoints continuously.
  • It is rule-based and only supports a focused subset of Linux SSH syslog formats.
  • Traditional syslog timestamps lack a year and timezone; the CLI accepts a year, and parsed timestamps are timezone-naive.
  • It does not block IP addresses, perform threat-intelligence lookups, or integrate with a SIEM.
  • An alert is a triage lead. Confirming an incident requires additional identity, host, and network evidence.

Future work documented in the repository includes broader log-format support, MITRE ATT&CK mapping, optional threat-intelligence enrichment, and possible SIEM integration.
